# Reglas Doradas de Integridad de Datos (Data Integrity)

1. **Montos Enteros Obligatorios**: Bajo NINGUNA circunstancia los montos de dinero (precios, costos, saldos) se manejarán como decimales de coma flotante numérico en lógica o DB (`*_cents`). TODO cálculo de dinero debe ejecutarse como ENTEROS EN CENTAVOS. Para garantizar la consistencia en el parseo y la serialización segura a strings decimales hacia el cliente (OWASP A02), es **obligatorio utilizar la clase `Money`** del paquete `@core/shared`. Queda prohibido manipular centavos manualmente.
2. **Operaciones Atómicas de Inventario**: El stock de un producto no puede ser modificado con una operación de asignación `(stock = nuevo_valor)`. Todas las rebajas y adiciones DEBEN ser relacionales y atómicas `(stock = stock - reserva)`. La estrategia de concurrencia por orden de precedencia es: (1°) **Bloqueo pesimista** `SELECT ... FOR UPDATE` dentro de una transacción (mecanismo principal, previene la race condition). (2°) **CHECK constraint** en la columna `stock >= 0` en la DB como última línea de defensa (detecta pero no previene; complemento, no reemplazo del bloqueo). Nunca depender solo del check para prevenir venta por debajo de 0.
3. **Máquina de Estados Estricta**: Las entidades críticas (como Pedidos, Envíos, Liquidaciones) solo pueden transitar a estados legalmente permitidos. (Ej: de `creada` a `pagada`, no de `creada` a `entregada`). Todas las transiciones deben estar reguladas centralizadamente (usando una función tipo `validarTransicion` o una máquina de estados).
4. **Idempotencia en Mensajes y API**: Los manejadores de eventos (Consumers de RabbitMQ) deben ser **idempotentes**. Dado que la entrega "At-Least-Once" puede entregar un mensaje dos veces, la lógica debe validar si el evento ya fue procesado. Asimismo, los endpoints de API mutativos críticos (crear pedido, cobrar) deben aceptar y requerir un header `Idempotency-Key` enviado por el **cliente** (app móvil, frontend, otro servicio). El microservicio receptor es responsable de **persistir** ese key (en Redis o en la misma DB del dominio) y detectar peticiones repetidas antes de ejecutar la lógica, retornando el resultado original en lugar de duplicar la acción. **TTL de claves de idempotencia:** Deben tener un TTL distinto al de la caché operacional: mínimo **24 horas** para operaciones financieras (cobros, liquidaciones) y mínimo **1 hora** para operaciones de inventario. No aplicar los TTLs cortos de caché de `architecture.md` regla 7 a este mecanismo.
5. **Principio de Partida Doble en Finanzas**: Cualquier transacción contable o de comisiones debe respetar la partida doble; el total de débitos y créditos en un movimiento deben sumar exactamente a cero. Ningún asiento desbalanceado puede persistirse.
6. **Manejo de Deadlocks**: Asegurar un orden lexicográfico predecible al actualizar múltiples filas en una base de datos de manera atómica, para evitar condiciones de bloqueo fatal (Deadlocks).
