# Reglas Doradas de Arquitectura (Architecture)

1. **CQRS y Event Sourcing Exclusivo por Dominio**: El patrón CQRS y Event Sourcing se utilizará **únicamente** en servicios con alta tasa de escritura o criticidad de auditoría histórica (como `orders-service`). Los demás servicios (baja escritura) utilizarán CRUD convencional para no añadir complejidad innecesaria.
2. **Comunicación Asíncrona (Coreografía)**: Ninguna **mutación crítica** (escrituras, cambios de estado, cobros, reservas de stock) puede depender de una llamada HTTP síncrona a otro microservicio. Toda orquestación distribuida de este tipo DEBE realizarse a través del broker de mensajería (RabbitMQ) usando eventos de dominio descriptivos en español (ej: `pedido.creado`, `stock.reservado`, `liquidacion.cerrada`) — consistente con la convención de idioma del dominio en `naming-conventions.md` regla 6. **Excepción permitida:** las llamadas HTTP síncronas a otro servicio para **consultas de solo lectura idempotentes** son aceptables cuando: (a) no existe un evento previo que sincronice el dato localmente, (b) la latencia añadida está dentro del SLA, (c) la dependencia está documentada en el ADR, **y (d) el servicio llamador implementa obligatoriamente un circuit breaker o degradación elegante** (retornar respuesta cacheada o parcial) si el servicio dependiente no responde — garantizando la autonomia definida en la regla 5. Sin la condición (d), la excepción no es válida.
3. **Consistencia Eventual Mediante Outbox**: Nunca enviar eventos al broker en medio de una transacción de negocio y asumir éxito. Es **obligatorio** usar el patrón Outbox. Los eventos de dominio generados deben escribirse en la tabla de outbox del dominio dentro de la **misma transacción** local de la base de datos de la lógica de negocio. El nombre de esta tabla nunca debe hardcodearse; debe leerse obligatoriamente de la variable de entorno `OUTBOX_TABLA` (ej. `orders.outbox`) para que el `OutboxService` centralizado pueda realizar el polling correctamente.
4. **Resiliencia Mediante DLQ (Dead Letter Queue)**: Todo consumidor de eventos en RabbitMQ debe estar encolado con mecanismos de reintento. Tras superar la política de reintentos (`REINTENTOS_MAXIMOS`), el mensaje debe enrutarse a una cola de mensajes muertos (DLQ) para análisis manual e inyección controlada, sin bloquear la cola principal.
5. **Autonomía de los Microservicios (Bounded Contexts)**: Un microservicio debe ser completamente autónomo. Si otro servicio se cae, el servicio actual debe seguir operando (quizás degradado) utilizando la caché o los eventos ya sincronizados.
6. **Capa Anticorrupción (ACL)**: Cuando un microservicio se integre con un servicio externo (pasarelas de pago, logística de terceros), debe existir un adaptador o ACL que aísle nuestro modelo de dominio del modelo externo.
7. **Estrategia de Caché (TTL Obligatorio)**: La caché (si se usa, e.g. Redis) solo debe almacenar datos transitorios o de lectura masiva. Nunca debe ser la fuente de la verdad. Toda actualización en base de datos debe invalidar explícitamente su respectiva caché. Además, **todo dato en caché debe tener un TTL máximo definido** (ej. 60 segundos para catálogos, 5 minutos para datos públicos) para garantizar que, si el servicio propietario cae y no puede invalidar, los datos obsoletos expiren automáticamente y no persistan de forma indefinida.
