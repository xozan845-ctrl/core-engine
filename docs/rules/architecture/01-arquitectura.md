# 01 — Reglas Doradas de Arquitectura

Aplica a: estilo arquitectónico, comunicación entre servicios, resiliencia y
estrategias de caché de los microservicios de Core Engine.

## Reglas

| ID | Regla |
|---|---|
| R-AR-1 | **CQRS y Event Sourcing exclusivo por dominio**: el patrón CQRS y Event Sourcing se utilizará **únicamente** en servicios con alta tasa de escritura o criticidad de auditoría histórica (como `orders-service`). Los demás servicios (baja escritura) utilizarán CRUD convencional para no añadir complejidad innecesaria. |
| R-AR-2 | **Comunicación asíncrona (coreografía)**: ninguna **mutación crítica** (escrituras, cambios de estado, cobros, reservas de stock) puede depender de una llamada HTTP síncrona a otro microservicio. Toda orquestación distribuida de este tipo DEBE realizarse a través del broker de mensajería (RabbitMQ) usando eventos de dominio descriptivos en español (ej: `pedido.creado`, `stock.reservado`, `liquidacion.cerrada`) — consistente con la convención de idioma del dominio en `R-NC-6` (`02-naming.md`). **Excepción permitida:** las llamadas HTTP síncronas a otro servicio para **consultas de solo lectura idempotentes** son aceptables cuando: (a) no existe un evento previo que sincronice el dato localmente, (b) la latencia añadida está dentro del SLA, (c) la dependencia está documentada en el ADR, **y (d) el servicio llamador implementa obligatoriamente un circuit breaker o degradación elegante** (retornar respuesta cacheada o parcial) si el servicio dependiente no responde — garantizando la autonomía definida en `R-AR-5`. Sin la condición (d), la excepción no es válida. |
| R-AR-3 | **Consistencia eventual mediante Outbox**: nunca enviar eventos al broker en medio de una transacción de negocio y asumir éxito. Es **obligatorio** usar el patrón Outbox. Los eventos de dominio generados deben escribirse en la tabla de outbox del dominio dentro de la **misma transacción** local de la base de datos de la lógica de negocio. El nombre de esta tabla nunca debe hardcodearse; debe leerse obligatoriamente de la variable de entorno `OUTBOX_TABLA` (ej. `orders.outbox`) para que el `OutboxService` centralizado pueda realizar el polling correctamente. |
| R-AR-4 | **Resiliencia mediante DLQ (Dead Letter Queue)**: todo consumidor de eventos en RabbitMQ debe estar encolado con mecanismos de reintento. Tras superar la política de reintentos (`REINTENTOS_MAXIMOS`), el mensaje debe enrutarse a una cola de mensajes muertos (DLQ) para análisis manual e inyección controlada, sin bloquear la cola principal. |
| R-AR-5 | **Autonomía de los microservicios (bounded contexts)**: un microservicio debe ser completamente autónomo. Si otro servicio se cae, el servicio actual debe seguir operando (quizás degradado) utilizando la caché o los eventos ya sincronizados. |
| R-AR-6 | **Capa anticorrupción (ACL)**: cuando un microservicio se integre con un servicio externo (pasarelas de pago, logística de terceros), debe existir un adaptador o ACL que aísle nuestro modelo de dominio del modelo externo. |
| R-AR-7 | **Estrategia de caché (TTL obligatorio)**: la caché (si se usa, e.g. Redis) solo debe almacenar datos transitorios o de lectura masiva. Nunca debe ser la fuente de la verdad. Toda actualización en base de datos debe invalidar explícitamente su respectiva caché. Además, **todo dato en caché debe tener un TTL máximo definido** (ej. 60 segundos para catálogos, 5 minutos para datos públicos) para garantizar que, si el servicio propietario cae y no puede invalidar, los datos obsoletos expiren automáticamente y no persistan de forma indefinida. |
