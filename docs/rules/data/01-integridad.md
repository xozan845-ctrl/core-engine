# 01 — Reglas Doradas de Integridad de Datos

Aplica a: dinero, inventario, estados, idempotencia y contabilidad en todos los
dominios transaccionales de Core Engine.

## Reglas

| ID | Regla |
|---|---|
| R-DI-1 | **Montos enteros obligatorios**: bajo NINGUNA circunstancia los montos de dinero (precios, costos, saldos) se manejarán como decimales de coma flotante numérico en lógica o DB (`*_cents`). TODO cálculo de dinero debe ejecutarse como ENTEROS EN CENTAVOS. Para garantizar la consistencia en el parseo y la serialización segura a strings decimales hacia el cliente (OWASP A02), es **obligatorio utilizar la clase `Money`** del paquete `@core/shared`. Queda prohibido manipular centavos manualmente. |
| R-DI-2 | **Operaciones atómicas de inventario**: el stock de un producto no puede ser modificado con una operación de asignación `(stock = nuevo_valor)`. Todas las rebajas y adiciones DEBEN ser relacionales y atómicas `(stock = stock - reserva)`. La estrategia de concurrencia por orden de precedencia es: (1°) **bloqueo pesimista** `SELECT ... FOR UPDATE` dentro de una transacción (mecanismo principal, previene la race condition); (2°) **CHECK constraint** en la columna `stock >= 0` en la DB como última línea de defensa (detecta pero no previene; complemento, no reemplazo del bloqueo). Nunca depender solo del check para evitar venta por debajo de 0. |
| R-DI-3 | **Máquina de estados estricta**: las entidades críticas (como Pedidos, Envíos, Liquidaciones) solo pueden transitar a estados legalmente permitidos (ej: de `creada` a `pagada`, no de `creada` a `entregada`). Todas las transiciones deben estar reguladas centralizadamente (usando una función tipo `validarTransicion` o una máquina de estados). |
| R-DI-4 | **Idempotencia en mensajes y API**: los manejadores de eventos (consumers de RabbitMQ) deben ser **idempotentes**. Dado que la entrega "At-Least-Once" puede entregar un mensaje dos veces, la lógica debe validar si el evento ya fue procesado. Asimismo, los endpoints de API mutativos críticos (crear pedido, cobrar) deben aceptar y requerir un header `Idempotency-Key` enviado por el **cliente** (app móvil, frontend, otro servicio). El microservicio receptor es responsable de **persistir** ese key (en Redis o en la misma DB del dominio) y detectar peticiones repetidas antes de ejecutar la lógica, retornando el resultado original en lugar de duplicar la acción. **TTL de claves de idempotencia:** deben tener un TTL distinto al de la caché operacional: mínimo **24 horas** para operaciones financieras (cobros, liquidaciones) y mínimo **1 hora** para operaciones de inventario. No aplicar los TTLs cortos de caché de `R-AR-7` (`../architecture/01-arquitectura.md`) a este mecanismo. |
| R-DI-5 | **Principio de partida doble en finanzas**: cualquier transacción contable o de comisiones debe respetar la partida doble; el total de débitos y créditos en un movimiento deben sumar exactamente a cero. Ningún asiento desbalanceado puede persistirse. |
| R-DI-6 | **Manejo de deadlocks**: asegurar un orden lexicográfico predecible al actualizar múltiples filas en una base de datos de manera atómica, para evitar condiciones de bloqueo fatal (deadlock). |
